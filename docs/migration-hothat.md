# План переезда kabinetdoma.ru на hothat: от второго сайта до приёмки

Рабочая версия от 2026-11-19 (первая — 2026-11-16, T-073). Переезд ещё не выполнен: это
инструкция, по которой он делается за один вечер, с точками отката на каждом шаге.
Всё, что в панели и в кабинете регистратора, делает владелец; всё, что в репозитории, —
разработка (T-090). Второй сайт владельца `trvl4.me` уже работает на этом же аккаунте hothat,
и его трогать нельзя.

## 0. Выделенный IP: он у аккаунта уже есть

**Выделенный адрес уже выдан — `178.57.216.221`** (cPanel → «Общая информация»,
строка «Dedicated IP Address»). Покупать ничего не нужно, он входит в тариф и один на весь
аккаунт: `trvl4.me` отвечает с него же. Для переезда это удобно, а не обязательно:

- в nic.ru в `A @` идёт **один** адрес вместо четырёх адресов Pages, откат — одна строка;
- сайт проверяется по IP до смены DNS (`curl --resolve`), окно «посетитель видит заглушку»
  не появляется вовсе;
- своя PTR-запись возможна, но для переезда не нужна.

Ниже — почему выделенный IP для переезда не был обязателен: аргументы остаются верными, если
панель когда-нибудь покажет общий адрес. Причины по порядку:

1. **HTTPS от IP не зависит.** Сертификат выбирается по имени из TLS-расширения SNI, поэтому
   на одном общем IP cPanel спокойно держит сколько угодно сертификатов — по одному на домен
   (документация cPanel, «Guide to SSL», раздел SNI). AutoSSL выпишет Let's Encrypt и на
   `kabinetdoma.ru`, и на `www.kabinetdoma.ru`, и на `trvl4.me` одновременно.
2. **Сайты различаются по имени, а не по адресу.** Apache раскладывает запросы по vhost'ам:
   `kabinetdoma.ru` попадёт в свой каталог, `trvl4.me` — в свой. IP у них общий, и это норма
   для shared-хостинга.
3. **В cPanel IP один на аккаунт.** Даже если бы владелец купил выделенный IP, он всё равно
   был бы общим для `trvl4.me` и `kabinetdoma.ru`, то есть заявленная «изоляция от соседей»
   внутри аккаунта не появилась бы.
4. **На SEO и скорость IP не влияет.** Это не сигнал ранжирования, а скорость зависит от
   сервера и кэша, а не от того, делим ли мы адрес с другими сайтами.

Когда выделенный IP действительно имеет смысл (не наш случай, но чтобы знать):

- своя PTR-запись и репутация при **массовых** рассылках (у нас письма — единичные ответы,
  и идут они через почтовый сервер провайдера, а не напрямую с нашего IP);
- контрагент вписал наш IP в allowlist (у нас таких нет);
- нужен сервис на нестандартном порту (не нужно — только 80/443);
- в договоре прямо написано «неразделяемый адрес» (не наш случай).

Если всё же захочется: на сайте hothat услуги выделенного IP нет, спрашивать у
support@hothat.ru. Для переезда это лишние расходы и лишний шаг, брать не советую.

## 2. За 1–2 дня: подготовка (15 минут, владелец)

1. **Записать три факта из панели** — они понадобятся во всех шагах:
   - **выделенный IP — `178.57.216.221`** (cPanel → «Общая информация», «Dedicated IP Address»);
     он и пойдёт в `A @` на шаге 3. Если панель покажет рядом и «Shared IP» — он не нужен;
   - **`pwd`** — это команда: её печатают в терминале после входа по SSH, и она выводит текущий
     каталог, то есть домашний каталог аккаунта. Вывод вида `/home/<аккаунт>` и есть «абсолютный
     путь аккаунта»: из него собираются `Repository Path` клона, строка rsync
     (`/home/<аккаунт>/kabinetdoma.ru/`) и проверка, куда смотрит домен. В панели тот же путь
     виден в «Домены» как корневая папка `/kabinetdoma.ru` — это сокращение от
     `/home/<аккаунт>/kabinetdoma.ru`;
   - точная строка подключения по SSH: хост, порт (обычно 22) и логин — он же имя аккаунта
     из `pwd` (в письме hothat или в разделе «SSH-доступ»; там же ключ или пароль).
2. **Проверить место.** Тариф «Пять» — 5 ГБ; сайт занимает 9,7 МБ, клон репозитория ~30 МБ
   (в GitHub репозиторий весит 8,3 МБ), бэкапы панели отдельно. cPanel → «Disk Usage»: свободного места должно быть больше 1 ГБ.
3. **Проверить бэкапы.** cPanel → «Backup» / «Backup Wizard»: ежедневный бэкап включён,
   восстановление доступно. Если раздел не включён — написать в поддержку до переезда.
4. **Проверить SSL.** cPanel → «SSL/TLS Status»: виден ли `trvl4.me` с зелёным сертификатом и
   включён ли AutoSSL (Let's Encrypt). Если AutoSSL выключен — включить.
5. **Ничего не менять в `trvl4.me`**: ни document root, ни `.htaccess`, ни сертификат, ни почту.
   Все шаги ниже делаются только с `kabinetdoma.ru` и его каталогом.

## 3. Шаг 1. Создать второй сайт в cPanel (15 минут, владелец)

Это тот самый шаг, с которого начинается переезд: пока в панели нет домена и каталога,
заливать файлы некуда, а сертификат выпускать не на что.

1. cPanel → раздел **«Домены»** (в старых сборках — **«Addon Domains»**, «Дополнительные
   домены»).
2. Нажать **«Создать новый домен»** («Create A New Domain»).
3. Заполнить:
   - **Домен:** `kabinetdoma.ru` — без `www`, без `https://`, без слэша на конце;
   - **«Share document root»** («Общий корневой каталог») — снять галочку: только после этого
     панель покажет два оставшихся поля;
   - **Поддомен:** `kabinetdoma` → в поле получится `kabinetdoma.trvl4.me`. Это служебное имя,
     посетители его не видят (пункт 4);
   - **Корневая папка:** `/home/<аккаунт>/kabinetdoma.ru` — панель подставит путь сама, можно
     оставить предложенный; если версия панели не пускает за пределы `public_html` —
     `public_html/kabinetdoma.ru` (почему первый вариант лучше — пункт 5);
   - отправить форму.
4. **Поле «поддомен» — не ошибка и не второй сайт.** Так устроены дополнительные домены
   в cPanel: второй домен на аккаунт напрямую не вешается, панель создаёт в фоне поддомен
   основного (`kabinetdoma.trvl4.me`), ставит его vhost'ом на нужную папку и привязывает
   `kabinetdoma.ru` алиасом к нему (документация cPanel: «Why is a subdomain created for my
   addon domain»). Отсюда следствия:
   - имя поддомена — любое свободное, кроме `www`, `mail` и уже занятых (`kabinetdoma`, `kd`,
     `dom` — на работу сайта не влияет); в списке доменов будет виден только `kabinetdoma.ru`;
   - `kabinetdoma.trvl4.me` в интернете не появится и `trvl4.me` не изменит: у него нет своих
     файлов, он смотрит в тот же отдельный каталог, а публичный DNS ему не нужен (запись будет
     только в локальной зоне, если DNS `trvl4.me` ведёт hothat);
   - удалить этот поддомен по отдельности нельзя, пока живёт `kabinetdoma.ru` — это нормально,
     он удаляется вместе с доменом;
   - **через «Subdomains» его не создавать**: сайт добавляется именно через «Домены» /
     «Addon Domains», иначе у `kabinetdoma.ru` не будет своего vhost. Старая форма «Addon
     Domains» спрашивает те же три поля в том же порядке: домен, поддомен, корневая папка.
5. **Почему корень лучше вне `public_html`.** `/home/<аккаунт>/kabinetdoma.ru` лежит рядом
   с `public_html`, и правила из `.htaccess` основного сайта (`public_html/.htaccess`, а
   у `trvl4.me` он в корне) до него не достают: Apache применяет `.htaccess` ко вложенным
   каталогам, поэтому внутри `public_html` чужие `RewriteRule` и редиректы могут цеплять наш
   сайт. Побочный эффект вложенного варианта — дубль по адресу `trvl4.me/kabinetdoma.ru/`,
   который поисковикам не нужен. Если версия панели разрешает только `public_html/...`, берём
   `public_html/kabinetdoma.ru` и после заливки проверяем пункт 13 из §7 (нет ли редиректа от
   правил `trvl4.me`).
6. **Почему галочку обязательно снять.** Если оставить «Share document root», файлы нового
   сайта положатся в корень основного домена — то есть поверх `trvl4.me`. Это единственный
   шаг, которым можно сломать соседний сайт, поэтому проверить путь глазами до нажатия.
7. **Что появится:** отдельный vhost, каталог `/home/<аккаунт>/kabinetdoma.ru` с заглушкой
   `index.html`, алиас `www.kabinetdoma.ru` на тот же каталог. Почту, поддомены и базы здесь
   не создавать — не нужны.
8. **Если панель ругается, что домен не указывает на этот сервер** — это ожидаемо и не ошибка:
   A-записи ещё на GitHub. Домен всё равно создаётся (предупреждение, не отказ). Если панель
   именно блокирует сохранение — перейти к шагу 5 (DNS), вернуться сюда и создать домен сразу
   после переключения. Тогда порядок такой: DNS → домен → файлы, и между переключением и
   заливкой сайт на 5–10 минут покажет заглушку хостинга.
9. **Проверить, что `trvl4.me` цел:** открыть `https://trvl4.me` — отдаётся его сайт; в списке
   доменов у него прежний document root. Если путь изменился — немедленно вернуть.
10. Записать в заметки: `document root = /home/<аккаунт>/kabinetdoma.ru` (панель показывает его
    как `/kabinetdoma.ru`), служебный поддомен = `kabinetdoma.trvl4.me` / `kabinetdoma.ru.trvl4.me`
    (не публикуется, ничего не делает), выделенный IP = `178.57.216.221`.

## 4. Шаг 2. Залить сайт до переключения DNS (40 минут, разработка + владелец)

Смысл шага: к моменту смены A-записей сайт уже лежит на месте и проверен по IP, поэтому окно
«пользователь видит заглушку» равно нулю, а откат — это только возврат DNS.

**Что уезжает.** Только публикуемый состав: `index.html`, `404.html`, `robots.txt`,
`sitemap.xml`, `.htaccess`, каталоги `article`, `articles`, `about`, `builder`, `calculator`,
`catalog`, `checklist`, `privacy`, `terms`, `tests`, `assets`, `data`, `images`, файлы
иконок/логотипов, `og-image.jpg`, подтверждения поисковиков (`google*.html`, `yandex*.html`).
`docs/`, `tools/`, `app/`, `content/`, `*.md`, `CNAME`, `.nojekyll`, `_redirects` не уезжают.
Список живёт в одном месте — `tools/public-manifest.txt` (T-090, готов 19.11): его читают
`.cpanel.yml`, `tools/deploy-hothat.sh` и `verify-build`.

**Какой репозиторий клонировать.** Только рабочий — `trvlfourme/trvlfourme.github.io`: в нём
рядом с составом сайта лежат `tools/public-manifest.txt`, `.htaccess` и `.cpanel.yml`. Прод-
репозиторий `mail4startups-creator/home4work`, куда раньше отправлял выкладки `tools/deploy-prod.sh` (теперь он в `tools/archive/`), —
это готовая публикация без `tools/`, `.cpanel.yml` и `.htaccess` (проверено 19.11 по дереву
GitHub). Панель из него выложить не сможет: копировать нечего и запускать нечего.

**Вариант А (основной): клон из GitHub в панели Git™ Version Control.**

Как это устроено: панель делает обычный `git clone` в каталог внутри аккаунта — например
`/home/<аккаунт>/repositories/kabinetdoma`, **не** в корень сайта. Кнопка «Deploy HEAD Commit»
запускает bash-команды из `.cpanel.yml` (файл лежит в корне репозитория и приезжает с клоном),
а они копируют публикуемый состав в `/home/<аккаунт>/kabinetdoma.ru`. Клон и сайт — два разных
каталога, поэтому `.git`, `docs/`, `tools/`, `app/` на сайте не появляются; это и есть главная
причина не клонировать прямо в document root.

**Перед первым клоном** в рабочую копию должен быть отправлен `main`: до 19.11 GitHub-копия
рабочего репозитория отставала на 153 коммита, поэтому `ea40a8b` с `.cpanel.yml` до неё не
доехал — панель видела в клоне пустой корень и отключала Deploy. `git push origin main` — это
не выкладка: сайт обновляют кнопки панели («Update from Remote» → «Deploy HEAD Commit»),
запасной путь — `tools/deploy-hothat.sh --push`.

1. **Создать клон.** cPanel → «Files» → **«Git™ Version Control»** → «Create»:
   - тумблер **«Clone a Repository»** — включить;
   - **Clone URL:** `https://github.com/trvlfourme/trvlfourme.github.io.git` (репозиторий
     публичный: логин и токен не нужны, а `user:password@` панель в URL не принимает);
   - **Repository Path:** `repositories/kabinetdoma` — путь относительно домашнего каталога,
     полный получится `/home/<аккаунт>/repositories/kabinetdoma`;
   - **Repository Name** (если поле есть): `kabinetdoma`;
   - «Create» и подождать: клон ~30 МБ, пока он идёт, в списке может не быть HEAD — это нормально.
2. **Если «Create» вернул ошибку**, причина почти всегда одна из трёх: неверный Clone URL
   (адрес должен заканчиваться на `.git`), путь внутри служебного каталога (`.cpanel`, `.ssh`,
   `mail`, `ssl`, `tmp`, `etc`, `logs`, `cgi-bin` — там cPanel репозитории запрещает) или
   пробел/спецсимвол в пути (кавычки, `$`, `#`, `%`, скобки, `;`, `=`, `:` и т.п. нельзя;
   буквы, цифры, дефис, точка, подчёркивание и слэш — можно).
3. **Первая выкладка.** «Manage» у репозитория → вкладка «Pull or Deploy» →
   **«Deploy HEAD Commit»**. Только эта кнопка копирует файлы на сайт: `git pull` сам по себе
   сайт не обновляет.
4. **Проверить результат** в File Manager: в `kabinetdoma.ru` есть `index.html`, `.htaccess`,
   каталоги `article`, `assets`, …; `docs/`, `tools/`, `.git` там нет. Дальше — проверка по IP.
5. **Обновление в будни — две кнопки по порядку:** «Update from Remote» (это `git pull --ff-only`,
   забирает коммиты из GitHub) → «Deploy HEAD Commit» (запускает `.cpanel.yml`). Между ними само
   ничего не произойдёт — так устроена панель.
6. **Деплой выключен, кнопки серые.** Панель пишет два требования: «A valid .cpanel.yml file
   exists» и «no uncommitted changes in the checked-out branch». Первое и было причиной 19.11:
   файл лежал в рабочей копии (`ea40a8b`), но не в GitHub — панель его не видела. Второе значит,
   что файлы в клоне правили руками: `cd ~/repositories/kabinetdoma && git status` покажет,
   `git checkout -- .` вернёт. Поэтому `.cpanel.yml` правят в репозитории и пушат, а на сервере
   не редактируют. Если после «Update from Remote» кнопка всё ещё серая — клон сделан из
   `mail4startups-creator/home4work`: такой клон удаляют и создают заново по URL рабочего
   репозитория.
7. **Автоматизация (не обязательна).** «Deploy HEAD Commit» = команда
   `/usr/local/cpanel/bin/uapi VersionControlDeployment create repository_root=/home/<аккаунт>/repositories/kabinetdoma`
   (на CloudLinux с этим префиксом, на обычных сборках — `/usr/bin/uapi`; в ответе `status: 1`
   и `log_path` с журналом задач). Значит, выкладка делается одной строкой по SSH:
   `cd ~/repositories/kabinetdoma && git pull --ff-only && /usr/local/cpanel/bin/uapi VersionControlDeployment create repository_root=$PWD`
   — и при желании вешается в cron раз в 10 минут под `flock`, чтобы два запуска не наложились.
   **Push в GitHub cPanel не уведомляет:** webhook'а «из коробки» у Git Version Control нет
   (post-receive hook срабатывает только при push в сам cPanel-репозиторий, а мы пушим в GitHub).
   Для мгновенной выкладки — либо cron, либо rsync по SSH (вариант Б), либо GitHub Actions с
   SSH-ключом. При обновлениях несколько раз в неделю две кнопки — штатный режим.
8. **Когда репозиторий станет приватным (T-060).** По HTTPS панель приватный репозиторий не
   склонирует (логин/пароль не принимает), нужен SSH-ключ: `ssh-keygen -t ed25519 -f ~/.ssh/kd -C "<аккаунт>@kabinetdoma.ru"`
   без пароля, публичную часть `~/.ssh/kd.pub` → GitHub → Settings → Deploy keys (права на запись
   не нужны), в `~/.ssh/config` — `Host github.com` и `IdentityFile ~/.ssh/kd`, один раз
   `ssh -T git@github.com` (ответить `yes`, пропишется `known_hosts`), затем пересоздать репозиторий
   в панели с Clone URL `git@github.com:trvlfourme/trvlfourme.github.io.git`.
9. **Место.** Клон ~30 МБ + сайт 11 МБ — меньше 1 % тарифа в 5 ГБ; бэкапы панели считаются
   отдельно.

**Вариант Б (запасной и основной для автоматизации): rsync по SSH.**

Из рабочей копии: `tools/deploy-hothat.sh` собирает тот же публикуемый состав по манифесту,
проверяет, что в нём нет `docs/`, `tools/`, `*.md`, и отправляет `rsync -az --delete` в
`<логин>@<хост>:/home/<аккаунт>/kabinetdoma.ru/`. Ключ — в `.secrets/`, не в репозитории.
Плюс: одна команда, никакой рассинхронизации «клон обновился, но не задеплоился». Минус: нужен
SSH-ключ на хостинге (завести один раз: `ssh-keygen`, публичную часть — в
`~/.ssh/authorized_keys` через панель или поддержку).

**Права и кодировка.** Файлы 644, каталоги 755, `.htaccess` 644 — иначе Apache отдаёт 500.
Заливка по Git/rsync байты не меняет, HTML остаётся в CRLF; в File Manager файлы не
пересохранять (редактор может конвертировать переводы строк).

**Проверка до DNS** — по IP, с подменой имени, чтобы живой сайт не участвовал:

```bash
IP=178.57.216.221        # выделенный IP аккаунта
curl -sI --resolve kabinetdoma.ru:80:$IP http://kabinetdoma.ru/ | head -5
curl -s  --resolve kabinetdoma.ru:80:$IP http://kabinetdoma.ru/ | grep -o '<title>[^<]*' | head -1
curl -sI --resolve kabinetdoma.ru:80:$IP http://kabinetdoma.ru/article/rabochee-mesto-na-balkone/ | head -3
```

Ожидается `200` и наш `<title>`, а не заглушка хостинга. HTTPS на этом шаге проверять рано:
сертификата на имя ещё нет — ошибка TLS здесь нормальна.

## 5. Шаг 3. DNS на nic.ru (20 минут + TTL)

**За сутки** поставить TTL 300 у `A @` и будущей записи `www`: при TTL 3600 ошибка живёт до
часа, при 300 — до пяти минут.

| Запись | Сейчас | Станет |
|---|---|---|
| `A @` | 185.199.108.153, .109, .110, .111 | `178.57.216.221` (старые четыре удалить в той же правке) |
| `CNAME www` | нет | `kabinetdoma.ru` — вернуть, чтобы `www` работал и редиректил на apex |
| `AAAA @` | нет | нет: IPv6 у хостинга не заявлен |
| `MX @` | improvmx 10/20 | **не трогать** — почта переезжает отдельным окном (T-061) |
| `TXT @` SPF | improvmx | **не трогать** до T-061 |
| `TXT _dmarc` | `p=none` | **не трогать** |
| `TXT` подтверждений | Яндекс, Google, Дистрибуция | **не трогать**; файловые подтверждения уже в сайте |
| `NS` | nic.ru | **не трогать** |

Запись получается ровно как у `trvl4.me` (проверено 19.11 через `nslookup`): `A trvl4.me` =
`178.57.216.221`, `www.trvl4.me` — CNAME на `trvl4.me`. Причина одна: оба сайта живут на одном
аккаунте панели с одним выделенным IP. Для `kabinetdoma.ru` так же: `A @` = `178.57.216.221`,
`CNAME www` → `kabinetdoma.ru` (на своё имя, а не на `trvl4.me`).

Почему `www` возвращаем: cPanel уже создал для него алиас на тот же каталог, AutoSSL покроет
оба имени, а `.htaccess` отдаст один 301 на apex с сохранением пути. Это закрывает T-134
навсегда: имя `www` снова работает, но без ошибки сертификата.

Порядок: сначала `A @` (проверить `dig +short kabinetdoma.ru`), через 2–3 минуты — `CNAME www`
(`dig +short www.kabinetdoma.ru`). Оставлять старые A-записи вместе с новой нельзя: часть
посетителей будет годами попадать на GitHub, а откат станет непредсказуемым.

Окно, когда часть посетителей ещё видит Pages, — до истечения старого TTL (при 300 — до
5 минут). Контент там тот же, вреда нет.

## 6. Шаг 4. Сертификат и HTTPS (10 минут, владелец)

1. Убедиться, что домен уже резолвится на hothat: `dig +short kabinetdoma.ru` и
   `dig +short www.kabinetdoma.ru` дают `178.57.216.221`. **AutoSSL выписывает сертификат только
   на домены, которые указывают на этот сервер** (проверка через HTTP), поэтому шаг идёт после
   DNS.
2. cPanel → **«SSL/TLS Status»** → «Run AutoSSL». В списке должны быть оба имени:
   `kabinetdoma.ru` и `www.kabinetdoma.ru`, оба зелёные. `trvl4.me` не трогать — у него свой.
3. Проверка SAN:

```bash
openssl s_client -connect kabinetdoma.ru:443 -servername kabinetdoma.ru </dev/null 2>/dev/null \
  | openssl x509 -noout -text | grep -A1 "Subject Alternative Name"
```

В выводе — оба имени: `DNS:kabinetdoma.ru, DNS:www.kabinetdoma.ru`.
4. **Force HTTPS — только одним способом.** Рекомендую `.htaccess` (блок из шага 5 T-090):
   там же живут правило `www → apex` и заголовки, один источник правды. Галочку
   «Force HTTPS Redirect» в панели в этом случае не включать, иначе два редиректа сложатся в
   цепочку.
5. **HSTS** — через сутки нормальной работы, строкой в `.htaccess`
   (`Header always set Strict-Transport-Security "max-age=31536000"`), не в первый час.

**Чем это кончилось 19.11.2026** (проверено 2026-11-22): AutoSSL выпустил Let's Encrypt сразу
на два имени, SAN `DNS:kabinetdoma.ru, DNS:www.kabinetdoma.ru`, срок до 17.02.2027; на домене
один `A` → `178.57.216.221`, у `www` — отдельный `A` на тот же адрес, AAAA нет. Продление делает
сам AutoSSL примерно за 30 дней до срока, отдельного продления не нужно — раз в месяц смотреть
«SSL/TLS Status» в месячной проверке прода (T-136). Три сбоя этого шага, которые стоили времени,
вынесены в §12: права `750` на корень, битый `CNAME` у `www` и кэш сертификата в антивирусе
на ноутбуке.
