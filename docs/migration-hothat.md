# План переезда kabinetdoma.ru на hothat: от второго сайта до приёмки

Рабочая версия от 2026-11-19 (первая — 2026-11-16, T-073). Переезд ещё не выполнен: это
инструкция, по которой он делается за один вечер, с точками отката на каждом шаге.
Всё, что в панели и в кабинете регистратора, делает владелец; всё, что в репозитории, —
разработка (T-090). Второй сайт владельца `trvl4.me` уже работает на этом же аккаунте hothat,
и его трогать нельзя.

## 0. Коротко: выделенный IP не нужен

**Нет, отдельный выделенный IP для переезда не нужен и денег на него тратить не надо.**
Причины по порядку:

1. **HTTPS от IP не зависит.** Сертификат выбирается по имени из TLS-расширения SNI, поэтому
   на одном общем IP cPanel спокойно держит сколько угодно сертификатов — по одному на домен
   (документация cPanel, «Guide to SSL», раздел SNI). AutoSSL выпишет Let's Encrypt и на
   `kabinetdoma.ru`, и на `www.kabinetdoma.ru`, и на `trvl4.me` одновременно.
2. **Сайты различаются по имени, а не по адресу.** Apache раскладывает запросы по vhost'ам:
   `kabinetdoma.ru` попадёт в свой каталог, `trvl4.me` — в свой. IP у них общий, и это норма
   для shared-хостинга.
3. **В cPanel IP один на аккаунт.** Даже если бы владелец купил выделенный IP, он всё равно
   был бы общим для `trvl4.me` и `kabinetdoma.ru`, то есть заявленная «изоляция от соседей»
   внутри аккаунта не появилась бы.
4. **На SEO и скорость IP не влияет.** Это не сигнал ранжирования, а скорость зависит от
   сервера и кэша, а не от того, делим ли мы адрес с другими сайтами.

Когда выделенный IP действительно имеет смысл (не наш случай, но чтобы знать):

- своя PTR-запись и репутация при **массовых** рассылках (у нас письма — единичные ответы,
  и идут они через почтовый сервер провайдера, а не напрямую с нашего IP);
- контрагент вписал наш IP в allowlist (у нас таких нет);
- нужен сервис на нестандартном порту (не нужно — только 80/443);
- в договоре прямо написано «неразделяемый адрес» (не наш случай).

Если всё же захочется: на сайте hothat услуги выделенного IP нет, спрашивать у
support@hothat.ru. Для переезда это лишние расходы и лишний шаг, брать не советую.

## 2. За 1–2 дня: подготовка (15 минут, владелец)

1. **Записать три факта из панели** — они понадобятся во всех шагах:
   - `Shared IP Address` (cPanel → «Общая информация» / правый блок статистики);
   - абсолютный путь аккаунта: `pwd` по SSH (обычно `/home/<аккаунт>`) и `document root` сайта
     `trvl4.me` (cPanel → «Домены»);
   - точная строка подключения по SSH: хост, порт, логин (в письме hothat или в разделе
     «SSH-доступ»). SSH у hothat есть — заявлено на странице тарифов.
2. **Проверить место.** Тариф «Пять» — 5 ГБ; сайт занимает 9,7 МБ, клон репозитория ~90 МБ,
   бэкапы панели отдельно. cPanel → «Disk Usage»: свободного места должно быть больше 1 ГБ.
3. **Проверить бэкапы.** cPanel → «Backup» / «Backup Wizard»: ежедневный бэкап включён,
   восстановление доступно. Если раздел не включён — написать в поддержку до переезда.
4. **Проверить SSL.** cPanel → «SSL/TLS Status»: виден ли `trvl4.me` с зелёным сертификатом и
   включён ли AutoSSL (Let's Encrypt). Если AutoSSL выключен — включить.
5. **Ничего не менять в `trvl4.me`**: ни document root, ни `.htaccess`, ни сертификат, ни почту.
   Все шаги ниже делаются только с `kabinetdoma.ru` и его каталогом.

## 3. Шаг 1. Создать второй сайт в cPanel (15 минут, владелец)

Это тот самый шаг, с которого начинается переезд: пока в панели нет домена и каталога,
заливать файлы некуда, а сертификат выпускать не на что.

1. cPanel → раздел **«Домены»** (в старых сборках — **«Addon Domains»**, «Дополнительные
   домены»).
2. Нажать **«Создать новый домен»** («Create A New Domain»).
3. Заполнить:
   - **Домен:** `kabinetdoma.ru` — без `www`, без `https://`, без слэша на конце;
   - **Корневая папка:** снять галочку **«Share document root»** («Общий корневой каталог»)
     и указать `/home/<аккаунт>/kabinetdoma.ru` — панель подставит путь сама, можно оставить
     предложенный;
   - отправить форму.
4. **Почему галочку обязательно снять.** Если оставить «Share document root», файлы нового
   сайта положатся в корень основного домена — то есть поверх `trvl4.me`. Это единственный
   шаг, которым можно сломать соседний сайт, поэтому проверить путь глазами до нажатия.
5. **Что появится:** отдельный vhost, каталог `/home/<аккаунт>/kabinetdoma.ru` с заглушкой
   `index.html`, алиас `www.kabinetdoma.ru` на тот же каталог. Почту, поддомены и базы здесь
   не создавать — не нужны.
6. **Если панель ругается, что домен не указывает на этот сервер** — это ожидаемо и не ошибка:
   A-записи ещё на GitHub. Домен всё равно создаётся (предупреждение, не отказ). Если панель
   именно блокирует сохранение — перейти к шагу 5 (DNS), вернуться сюда и создать домен сразу
   после переключения. Тогда порядок такой: DNS → домен → файлы, и между переключением и
   заливкой сайт на 5–10 минут покажет заглушку хостинга.
7. **Проверить, что `trvl4.me` цел:** открыть `https://trvl4.me` — отдаётся его сайт; в списке
   доменов у него прежний document root. Если путь изменился — немедленно вернуть.
8. Записать в заметки: `document root = /home/<аккаунт>/kabinetdoma.ru`.

## 4. Шаг 2. Залить сайт до переключения DNS (40 минут, разработка + владелец)

Смысл шага: к моменту смены A-записей сайт уже лежит на месте и проверен по IP, поэтому окно
«пользователь видит заглушку» равно нулю, а откат — это только возврат DNS.

**Что уезжает.** Только публикуемый состав: `index.html`, `404.html`, `robots.txt`,
`sitemap.xml`, `.htaccess`, каталоги `article`, `articles`, `about`, `builder`, `calculator`,
`catalog`, `checklist`, `privacy`, `terms`, `tests`, `assets`, `data`, `images`, файлы
иконок/логотипов, `og-image.jpg`, подтверждения поисковиков (`google*.html`, `yandex*.html`).
`docs/`, `tools/`, `app/`, `content/`, `*.md`, `CNAME`, `.nojekyll`, `_redirects` не уезжают.
Список будет жить в одном месте — `tools/public-manifest.txt` (T-090), его читают и выкладка,
и `verify-build`.

**Вариант А (основной): клон из GitHub в панели.**

1. cPanel → **«Git™ Version Control»** → «Create» → «Clone a Repository»:
   - Clone URL: `https://github.com/mail4startups-creator/home4work.git`
   - Repository Path: `/home/<аккаунт>/repos/kabinetdoma`
   - Branch: `main`
2. Разработка кладёт в репозиторий `.cpanel.yml` (T-090) — задачи деплоя: скопировать
   публикуемый состав из клона в `/home/<аккаунт>/kabinetdoma.ru`, предварительно удалив
   прошлую версию каталогов.
3. В панели нажать **«Deploy HEAD Commit»** — файлы появятся в document root.
4. Обновление в будни: «Update from Remote» (git pull) → «Deploy HEAD Commit». Это две кнопки,
   не одна: pull сам по себе файлы на сайт не копирует.
5. Когда репозиторий закроют (T-060): в панели создать SSH-ключ, публичную часть добавить в
   GitHub как deploy key, Clone URL заменить на `git@github.com:mail4startups-creator/home4work.git`
   и клонировать заново — приватный репозиторий иначе не клонируется.

**Вариант Б (запасной и основной для автоматизации): rsync по SSH.**

Из рабочей копии: `tools/deploy-hothat.sh` собирает тот же публикуемый состав по манифесту,
проверяет, что в нём нет `docs/`, `tools/`, `*.md`, и отправляет `rsync -az --delete` в
`<логин>@<хост>:/home/<аккаунт>/kabinetdoma.ru/`. Ключ — в `.secrets/`, не в репозитории.
Плюс: одна команда, никакой рассинхронизации «клон обновился, но не задеплоился». Минус: нужен
SSH-ключ на хостинге (завести один раз: `ssh-keygen`, публичную часть — в
`~/.ssh/authorized_keys` через панель или поддержку).

**Права и кодировка.** Файлы 644, каталоги 755, `.htaccess` 644 — иначе Apache отдаёт 500.
Заливка по Git/rsync байты не меняет, HTML остаётся в CRLF; в File Manager файлы не
пересохранять (редактор может конвертировать переводы строк).

**Проверка до DNS** — по IP, с подменой имени, чтобы живой сайт не участвовал:

```bash
IP=<shared IP из панели>
curl -sI --resolve kabinetdoma.ru:80:$IP http://kabinetdoma.ru/ | head -5
curl -s  --resolve kabinetdoma.ru:80:$IP http://kabinetdoma.ru/ | grep -o '<title>[^<]*' | head -1
curl -sI --resolve kabinetdoma.ru:80:$IP http://kabinetdoma.ru/article/rabochee-mesto-na-balkone/ | head -3
```

Ожидается `200` и наш `<title>`, а не заглушка хостинга. HTTPS на этом шаге проверять рано:
сертификата на имя ещё нет — ошибка TLS здесь нормальна.

## 5. Шаг 3. DNS на nic.ru (20 минут + TTL)

**За сутки** поставить TTL 300 у `A @` и будущей записи `www`: при TTL 3600 ошибка живёт до
часа, при 300 — до пяти минут.

| Запись | Сейчас | Станет |
|---|---|---|
| `A @` | 185.199.108.153, .109, .110, .111 | один IP hothat из панели (старые четыре удалить в той же правке) |
| `CNAME www` | нет | `kabinetdoma.ru` — вернуть, чтобы `www` работал и редиректил на apex |
| `AAAA @` | нет | нет: IPv6 у хостинга не заявлен |
| `MX @` | improvmx 10/20 | **не трогать** — почта переезжает отдельным окном (T-061) |
| `TXT @` SPF | improvmx | **не трогать** до T-061 |
| `TXT _dmarc` | `p=none` | **не трогать** |
| `TXT` подтверждений | Яндекс, Google, Дистрибуция | **не трогать**; файловые подтверждения уже в сайте |
| `NS` | nic.ru | **не трогать** |

Почему `www` возвращаем: cPanel уже создал для него алиас на тот же каталог, AutoSSL покроет
оба имени, а `.htaccess` отдаст один 301 на apex с сохранением пути. Это закрывает T-134
навсегда: имя `www` снова работает, но без ошибки сертификата.

Порядок: сначала `A @` (проверить `dig +short kabinetdoma.ru`), через 2–3 минуты — `CNAME www`
(`dig +short www.kabinetdoma.ru`). Оставлять старые A-записи вместе с новой нельзя: часть
посетителей будет годами попадать на GitHub, а откат станет непредсказуемым.

Окно, когда часть посетителей ещё видит Pages, — до истечения старого TTL (при 300 — до
5 минут). Контент там тот же, вреда нет.

## 6. Шаг 4. Сертификат и HTTPS (10 минут, владелец)

1. Убедиться, что домен уже резолвится на hothat: `dig +short kabinetdoma.ru` и
   `dig +short www.kabinetdoma.ru` дают IP из панели. **AutoSSL выписывает сертификат только
   на домены, которые указывают на этот сервер** (проверка через HTTP), поэтому шаг идёт после
   DNS.
2. cPanel → **«SSL/TLS Status»** → «Run AutoSSL». В списке должны быть оба имени:
   `kabinetdoma.ru` и `www.kabinetdoma.ru`, оба зелёные. `trvl4.me` не трогать — у него свой.
3. Проверка SAN:

```bash
openssl s_client -connect kabinetdoma.ru:443 -servername kabinetdoma.ru </dev/null 2>/dev/null \
  | openssl x509 -noout -text | grep -A1 "Subject Alternative Name"
```

В выводе — оба имени: `DNS:kabinetdoma.ru, DNS:www.kabinetdoma.ru`.
4. **Force HTTPS — только одним способом.** Рекомендую `.htaccess` (блок из шага 5 T-090):
   там же живут правило `www → apex` и заголовки, один источник правды. Галочку
   «Force HTTPS Redirect» в панели в этом случае не включать, иначе два редиректа сложатся в
   цепочку.
5. **HSTS** — через сутки нормальной работы, строкой в `.htaccess`
   (`Header always set Strict-Transport-Security "max-age=31536000"`), не в первый час.

## 9. Шаг 7. Выкладка после переезда (30 минут, разработка)

- **Основная команда:** `bash tools/deploy-hothat.sh` (без флага — только проверка состава,
  с `--push` — отправка по SSH). Правило T-053 сохраняется: в публичный корень уезжают только
  страницы и ресурсы, `docs/`, `tools/`, `*.md`, `app/` — никогда; скрипт падает, если они
  попали в состав.
- **Из панели:** «Update from Remote» + «Deploy HEAD Commit». Подходит, когда под рукой нет
  терминала; занимает две минуты.
- **Cron `git pull` сам по себе ничего не выкладывает** — `.cpanel.yml` запускается кнопкой
  панели, а не после pull. Если нужна автоматика, то это либо rsync по cron с локальной
  машины, либо серверный скрипт, который после pull повторяет шаги `.cpanel.yml`. Для сайта,
  который обновляется несколько раз в неделю, автоматика не обязательна: выкладка по решению
  владельца — штатный режим.
- **Приватный репозиторий (T-060):** clone по SSH с deploy key; rsync-вариант от видимости
  репозитория не зависит.

## 10. Шаг 8. Почта — отдельным окном (T-061, 1 час, владелец)

Не в день переезда сайта: смена MX в тот же вечер означает, что при откате DNS письма уже
уехали на другой сервер.

1. В cPanel → «Email Accounts» завести `info@kabinetdoma.ru`, включить DKIM (галочка),
   скопировать DKIM-запись.
2. В nic.ru: добавить `default._domainkey`, поменять MX на почтовый сервер hothat, SPF на
   `v=spf1 include:<spf hothat> ~all` (ровно один SPF, старый improvmx убрать).
3. Первые сутки DMARC `p=none` (уже стоит), затем `p=quarantine`, позже `p=reject`.
4. Проверка: письмо на `info@` доходит, ответ уходит; в заголовке письма
   `Authentication-Results: spf=pass dkim=pass dmarc=pass`.
5. После этого T-061 закрывается, и только тогда политика (T-054) может писать «почта
   обрабатывается в РФ».

## 12. Риски и что делать

| Риск | Признак | Что делать |
|---|---|---|
| Файлы легли в корень `trvl4.me` | его сайт показывает наш или 404 | вернуть `document root` в панели, залить заново в отдельный каталог |
| Панель не даёт создать домен до смены DNS | ошибка сохранения | переключить A (шаг 3), создать домен, сразу залить файлы |
| AutoSSL не выпустил сертификат | красный статус, ошибка DCV | проверить `dig`, что оба имени смотрят на IP hothat, запустить повторно; если не помогло — тикет в поддержку, до этого не объявлять переезд |
| `500 Internal Server Error` | на любой странице | права 644/755, проверить `.htaccess` (синтаксис, `Options -Indexes` при запрете `AllowOverride`) |
| Нет `mod_headers`/`mod_expires` | заголовков и кэша нет, сайт работает | блоки `<IfModule>` уже это переживают; написать в поддержку, не критично |
| `www` не работает | NXDOMAIN или ошибка сертификата | вернуть CNAME, дождаться TTL, перезапустить AutoSSL |
| Старые A остались в зоне | часть запросов уходит на Pages | удалить, проверить `dig` с 1.1.1.1 и 8.8.8.8 |
| Кончилось место | ошибки записи в панели | сайт 10 МБ + клон 90 МБ, лимит 5 ГБ; почистить старые бэкапы |
| Почта пропала | письма не доходят | в день сайта MX не трогали — проверить, что записи MX/SPF не изменились |
